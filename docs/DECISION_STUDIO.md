# Decision Studio and bounded sensitivity audit

For the v4 conversation and draft-response workspace, see the [conversation guide](CONVERSATION_WORKSPACE.md). This page documents the existing declared-facts editor.

The local browser workspace opens with `roguard-studio --open` or `python -m roguard.studio --open`. The command prints a `127.0.0.1` URL and opens it if the browser can be launched; otherwise, copy the printed URL into a browser on the same computer. Press Ctrl+C in the terminal to stop the process. No account, model download, cloud service, or JavaScript package is required. The wheel contains the HTML, CSS, and JavaScript files.

The default **Guided v2** tab builds corrected D1/R1/S1 symbolic facts from Romanian or Ukrainian controls. It covers D1 source and support signals, R1 recipient scope and possible source of concern, and S1 response criteria. **Audit uncertainty** uses the [v2 input](../schema/v2-audit-input.schema.json): each S1 criterion has a separate unknown checkbox and can remain unresolved while other criteria are known. The audit enumerates all valid completions, names every reachable decision code, gives one symbolic witness per code, and ranks questions by the worst number of codes remaining after one answer. The ranking does not estimate probability or promise that one question settles the decision. **Check** and **Explore changes** use the earlier [v1 contract](../schema/v1-contract-input.schema.json) and require all S1 unknown checkboxes to be cleared; a visible error points to the v2 audit otherwise. **Check unknowns** retains the earlier v1.5 whole-array completion audit. No response or child-message text is accepted in this form. If an R1 policy string, recipient set, or scope list is unknown, its domain is unbounded and no stability certificate is issued. The fictional routing example fixes the principal to `minor`, item to `symbol`, and purpose to `A`; it checks one allowed recipient in that declared scope. Use the CLI for more complex symbolic policies.

The **Legacy check** tab accepts one ordinary [historical contract input](../schema/contract-input.schema.json) and renders the existing findings and any proposed-use result. The **Compare** tab accepts two complete historical inputs with the same shape and exactly one changed scalar, using the existing `roguard-contrast` rule. The **Explore changes** tab varies selected declared facts one at a time and shows the variants that change a finding's status or reason codes, or a composed-use decision. Load either symbolic sample to start. These three tabs use the historical six-category rules.

The same exploration is available without a browser:

```sh
roguard-explore examples/proposed_use_ro.json
roguard-explore --limit 256 examples/contracts_uk.json
roguard-v1-explore examples/v1_candidate_ro.json
roguard-v1-explore examples/v1_candidate_uk.json
roguard-v1-envelope examples/v1_candidate_ro.json
roguard-v1-envelope examples/v1_candidate_uk.json
roguard-v2-audit examples/v2_uncertainty_ro.json
roguard-v2-audit examples/v2_uncertainty_uk.json
```

The historical explorer generates deterministic variants for D1, G1, P1 and proposed-use boolean declarations; the D1 source role; small A1 count changes; the R1 proposed recipient among declared roles; P1 decision times near events and expiries; and each applicable S1 pass field. The guided v1 explorer varies D1 evidence states and source role; R1 recipient, declared-role membership, permission in the matching declared scope, and concern state; and S1 pass and applicability states where a single valid fact can change. Both validate each candidate with the corresponding checker, count invalid candidates separately, and stop after 128 attempts in the browser. The historical CLI limit is configurable from 1 to 512. `truncated: true` means additional candidates existed. They do **not** explore every imaginable policy, string, event-list edit, or language expression. A missing decision flip does not prove a rule robust, and a found flip does not prove the caller's facts are true. The v1 report identifies paths and target states without copying custom identifiers or text; recipient targets use their index in sorted declared roles. Standard S1 field codes are included because they are fixed taxonomy vocabulary.

The v1.5 [finite completion report](../schema/v1-envelope-report.schema.json) is a different audit. It holds known facts fixed and replaces each `null` D1 boolean with both Boolean values; an unknown D1 source role with each declared role; and unknown S1 applicability/pass fields with every valid state over the ten fixed field codes. The largest S1 sweep has 59,049 completions. A `stable` result means only that all enumerated completions give the same decision code. It does not certify the reason codes, the caller's declarations, taxonomy validity, language interpretation, or real-world safety. `sensitive` names all reachable decision codes without treating their frequencies as probabilities. `unbounded` means the missing routing policy facts have no finite declared domain; the report intentionally gives no possible-code list or completion count for that case. The report never echoes custom values. This exact audit complements the bounded one-fact explorer; neither measures model accuracy.

The v2 audit keeps that exact finite-completion rule and adds independently unknown S1 criteria. An omitted S1 field state is also `unknown`, so the [example cards](../examples/v2_uncertainty_ro.json) list all ten states explicitly for easy review. The first `next_questions` entry is the best **one-step** minimax choice: it minimizes the largest number of possible decision codes after an answer, then the sum of those branch counts, then the largest completion count. A path is omitted if every answer leaves the same set of decisions. The report makes no assumption that the three S1 states are equally likely. Its witnesses are possible symbolic completions, not evidence about a person. Read [v2 release scope](V2_RELEASE.md) before using the output in a study.

The Studio binds only to `127.0.0.1` on a randomly chosen port. POST requests require the page's random session token, a matching same-origin header, an exact loopback Host, JSON content type, and a body under 1 MiB. Responses disable caching, declare a restrictive content security policy, and do not echo malformed input values. The service logs no requests and keeps no input files. The interface sends the editor's raw JSON bytes to the Python parser, preserving large decimal spellings that JavaScript numbers would round. Other local processes with access to the machine still require ordinary operating-system isolation; this is a local research workspace, not a multi-user service. Do not expose its port through a proxy or enter real child disclosures into the symbolic examples.

All four views are read-only. A `pass`, `NO_*`, or `ready_for_human_decision` means only that supplied fictional rules and facts are internally consistent under the corresponding checker. No person is notified, no data is sent to a guardian, and no account setting changes. The tool does not classify authentic Romanian or Ukrainian child messages. Corrected v1 taxonomy reviews are owner-attested; held-out text-model accuracy validation remains open in [Release gates](RELEASE_GATES.md).
