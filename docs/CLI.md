# Read-only contract CLI

Install the lightweight package with `python -m pip install -e .`, then run `python -m roguard examples/routing_ro.json` or `roguard examples/routing_uk.json`. Pass `-` or omit the file argument to read one JSON object from standard input. The command prints one JSON report to standard output, returns a nonzero exit code for malformed input, and performs no network or external action.

For a local batch, use `python -m roguard --jsonl examples/contracts_mixed.jsonl`. The [four-card bilingual example](../examples/contracts_mixed.jsonl) demonstrates an allowed route, a conflicting route, a blocked unparsed output, and revoked permission. Each input line must contain one complete JSON object; the command checks **every** line before printing any result, then prints one compact JSON report per line in the original order. Blank or malformed lines fail with a line number and no partial output. The CLI rejects duplicate object keys and nonstandard `NaN`/`Infinity` constants in both file modes, so a later key cannot silently replace an earlier declared fact. This mode uses the same contract schema and never invokes a model or external service.

The input object requires `language` (`ro` or `uk`) and at least one contract or a `proposed_use` request. Field names are fixed; unknown or omitted fields are errors. These cards state **caller-supplied fictional rules**, not inferred authority:

For editor completion and basic shape checks, use the [JSON Schema](../schema/contract-input.schema.json) as an editor setting. Keep `$schema` out of the input object because the CLI accepts only contract fields. The schema covers structure, primitive types, nonnegative counts and times, and nonblank policy identifiers; the CLI additionally checks cross-field meaning, scopes, and permission chronology. Finite numeric spellings such as `1.0` count as integers under JSON Schema and are normalized at the CLI boundary. JSON numbers are parsed exactly as decimals, so large integer-valued spellings do not round through binary floating point. Each numeric token is limited to 128 characters; this CLI limit also applies on Python 3.9.0, where the interpreter has no built-in decimal-integer length guard.

| Contract key | Required fields | Meaning |
|---|---|---|
| `disclosure` | `source_role`, `safety_or_support_anchor`, `indirect_or_repeated_support_pattern`, `explicit_support_request` | Caller-reviewed D1 pattern facts. `source_role` is `minor`, `adult`, `other`, or `null`; flags are booleans or `null`. The checker does not read or validate a child's words. |
| `readability` | `declared_age`, `measured_words`, `max_words`; optional `text` | Integer or `null` values for a declared experimental word cap. If `text` is supplied, the CLI counts it locally and requires any non-null `measured_words` to agree. It does not measure comprehension. |
| `routing` | `principal`, `item`, `purpose`, `proposed_recipient`, `recipient_roles`, `allowed_by_scope` | `recipient_roles` is a string array or `null`. `allowed_by_scope` is an array of unique `{principal,item,purpose,recipients}` rules or `null`. No guardian role has implicit access. |
| `permission` | `principal`, `item`, `purpose`, `recipient`, `at`, `proposed_use`, `use_required`, `events` | `events` is a list of `{sequence,principal,item,purpose,recipient,action}` with optional `expires_at`. Actions are `grant`, `narrow`, `revoke`, `pause`, or `resume`; `narrow` ends permission for the exact named person, item, purpose, and recipient scope. A later `resume` cannot restore that scope without a new `grant`. Sequence values must be unique within the same scope. `use_required` explicitly states whether withholding an otherwise permitted use would fail the task. |
| `boundary` | `allowed_fields`, `protected_fields`, `required_fields`, `proposed_fields`, `prior_correction`, `renewed_request` | Each field set is a string array or `null`; flags are booleans. Required fields must be allowed, and protected fields cannot be allowed. `prior_correction` asserts that a **currently proposed protected field** was removed by an earlier correction; `renewed_request` asserts a later request. Both are caller declarations, not inferred history. A reappearing protected field yields `BOUNDARY_RECURRENCE` only when both flags hold. An unlisted field yields `UNAUTHORIZED_REUSE`, including after a correction; both codes can appear. |
| `gate` | `review_owner`, `model_output_parsed`, `accept_unparsed`, `external_action_branch`, `human_approval_required` | Booleans describe a proposed workflow, including how malformed model output and any external branch are handled. The CLI never executes that branch. |
| `support` | `applicable_fields`, `passed_fields` | Caller-reviewed S1 fields. Arrays use `acknowledgement`, `next_step`, `human_support`, `no_blame`, `no_secret_promise`, `no_leading_question`, `no_unsupported_guarantee`, or `no_dependency_pressure`. Every passed field must be applicable. The checker reports each declared failed field, but does not read a response or prove that the caller judged it correctly. |
| `proposed_use` | `external_action` | Optional composition request. The checker requires matching routing and permission scopes; an external branch also requires a matching gate. This field never triggers an action. |

The output follows the [report JSON Schema](../schema/contract-report.schema.json) version 2 and contains one finding per supplied contract, with `category`, `source_kind`, `decision_code`, `status` (`pass`, `incomplete`, or `review`), machine-readable `reason_codes`, and `evidence_basis`. `checked_categories` lists only categories actually assessed; `caller_facts_verified: false` and `language_verified: false` make the input limits explicit. A `pass` on one card is therefore a pass **under that caller's declarations for that card**, not a whole-conversation clearance. `review_suggested` is true if any supplied finding needs review or a composed use is proposed; it is **not** approval to notify someone. The Ukrainian result includes `taxonomy_status: draft_uk_v0.1` because the Ukrainian category wording has not received independent language or subject-matter review. No model is downloaded or invoked by this command.

## Check one proposed use across contracts

Run `roguard examples/proposed_use_ro.json`. The optional top-level `proposed_use` object contains only `external_action: true` or `false`. Its report has a separate `proposed_use` result. `ready_for_human_decision` means the supplied route and current permission are individually passing **and** name the same principal, item, purpose, and recipient. It is not authorization: the result always reports `action_taken: false` and `caller_facts_verified: false`, and `review_suggested` remains true. A revoked, expired, or missing permission never produces a ready result. Different scopes produce `SCOPE_MISMATCH` even when the two individual findings pass. For an external branch, a gate must be supplied, declare an external branch, and require human approval; malformed output must remain blocked. Missing inputs produce `incomplete`, while a contradictory or failing supplied card produces `review`. `proposed_use.incomplete` remains true if required facts are missing even when another supplied card also needs review. The same typed rule is available through `assess_proposed_use()` in Python and works with either language tag; it does not assess whether the language or the caller's declarations are correct.

The evidence-basis codes are `caller_judgment` for D1/S1, `declared_word_cap` for A1, `declared_policy` for R1, `declared_permission_state` or `declared_boundary` for P1, and `declared_workflow` for G1. The optional A1 text counter is local, but the cap and its age relevance are still supplied by the caller. Neither a false verification flag nor a passing finding means the tool inspected the truth of the declarations.

The optional readability `text` uses a fixed local count: contiguous Unicode letters or numbers form a word; combining marks stay with that word, and a single internal apostrophe or hyphen joins adjacent letters or numbers. Punctuation and whitespace separate words. The text is never copied into the report or written by the CLI. `count_words()` exposes the same rule as a Python function. The cap is still supplied by the caller, and no Romanian or Ukrainian age-based comprehension threshold is inferred.

Try `roguard examples/readability_text_ro.json` or `roguard examples/readability_text_uk.json` for neutral, locally counted A1 examples. Both use a caller-chosen three-word cap; only the Ukrainian example exceeds it.

If `model_output_parsed` is false and `accept_unparsed` is false, the gate reports `OUTPUT_BLOCKED` with `incomplete` status: the policy blocks use of that output and a reviewer can inspect the failed parse. If `accept_unparsed` is true, it reports `FAIL_OPEN` even when this particular output parsed, because the proposed workflow would accept a later malformed output.

The small [Romanian routing](../examples/routing_ro.json) and [Ukrainian routing](../examples/routing_uk.json) examples show the minimal route and gate checks. The [full Romanian](../examples/contracts_ro.json) and [full Ukrainian](../examples/contracts_uk.json) examples exercise all six taxonomy categories in one call, including permission revocation and a repaired boundary. The D1 and S1 facts are abstract declarations supplied by the caller. All items are symbolic. The CLI does not write its input to disk, but callers are responsible for where they store or send their own input and output. Do not commit real child messages to this repository.

## Compare one declared fact

`roguard-contrast examples/contrast_route_before.json examples/contrast_route_after.json` compares two valid contract inputs with the same language and shape. Exactly one scalar value must differ. The output identifies its JSON path and any resulting category status or reason-code change, without copying the input values. In the example, changing only the proposed recipient changes R1 from `pass` to `review`. This works with `ro` and `uk` declared contracts, invokes no model, and takes no external action. It is an audit of the caller's stated policy facts, not a test of child-language interpretation.

If both inputs include `proposed_use`, the contrast also reports any change to the composed-use status. For example, changing only `external_action` from false to true without a gate changes `ready_for_human_decision` to `incomplete`; `decision_changed` records this even when no individual category finding changes.

The two inputs follow the [contract input schema](../schema/contract-input.schema.json); the output follows the [contrast report schema](../schema/contract-contrast.schema.json).

## Check agreement between two evidence declarations

`roguard-agreement first.json second.json` compares two local D1/S1 evidence cards in the same language. Both files use the ordinary contract input shape, but may contain only `disclosure` and `support` cards. The tool checks each input with the same rules as `roguard`, then compares field values. Support-field arrays are treated as sets, so their order is irrelevant. It accepts Romanian and Ukrainian cards; Ukrainian taxonomy wording remains a draft.

If any declared fact differs, the result is `needs_adjudication`, names only the differing JSON paths, sets `agreed_report` to `null`, and suggests human review. If the declarations match but contain missing facts, it reports `incomplete`. Only matching, complete declarations receive a `concordant` result and a shared contract report. A matching `review` finding remains a review finding; agreement never clears it. The output contains no source text or declared field values, and the command performs no external action. It cannot tell whether the two files came from independent people or whether either judgment is correct; `reviewer_independence_verified`, `caller_facts_verified`, and `language_verified` remain false.

To create each D1 card without entering message text, use the local numeric form:

```sh
roguard-review-card --language ro > first.json
roguard-review-card --language ro > second.json
roguard-agreement first.json second.json
```

For Ukrainian cards, replace `ro` with `uk`. D1 is the default category. The prompts appear on standard error and accept only listed digits for the declared source role, safety/support anchor, indirect or repeated pattern, and explicit support request. The complete JSON card appears on standard output; an early end or three invalid answers produces no card. Choosing `unknown` writes `null`, so the ordinary checker reports `incomplete` rather than silently treating missing evidence as negative.

For S1, run `roguard-review-card --language ro --category S1 > support.json` (or `uk`). The form asks whether each of the eight support fields is applicable, then whether each applicable field passed. It accepts digits only and emits the `support` card expected by `roguard` and `roguard-agreement`. An unknown applicability or pass choice produces an incomplete card; zero applicable fields is also incomplete. No response wording is entered or saved. The form cannot validate the reviewer's interpretation, verify reviewer independence, or take any external action. Keep saved cards under the review process's access controls because they contain judgments about material seen elsewhere.

## Audit agreement across a reviewer batch

To prepare two blinded packets from an **attested abstract** batch, run `roguard-blind-packets --batch batch-0035 --category D1 --output-dir review_runs/pilot-0035`. The command writes `reviewer-a.jsonl` and `reviewer-b.jsonl` in different orders with the same random opaque item IDs. Each packet contains language, source kind, category, and the permitted abstract card text, but no source row ID or reference label. `owner-map.json` retains the ID mapping and exact packet hashes for the study owner; keep it separate from both reviewers. The destination must not already exist, and `review_runs/` is ignored by Git. S1 packets use `--category S1` with an attested batch containing response cards. This command does not validate that reviewers are independent or prevent someone with repository access from looking up generator labels; the study owner must control packet distribution and blinding.

On a reviewer's machine, place the packet in a private directory and run `roguard-annotate-packet review_runs/reviewer-a.jsonl review_runs/reviewer-a-answers.jsonl`. The local `review_runs/` directory is ignored by Git. The command walks through that reviewer's packet in order. It displays each permitted abstract card and its opaque ID, asks the same numbered D1/S1 questions as `roguard-review-card`, and appends one content-free answer row after each completed card. The answer file and its `reviewer-a-answers.jsonl.packet.json` binding are created with mode `0600`. The binding records the packet's SHA-256 before annotation; rerunning refuses changed packet bytes and resumes at the first unanswered row after checking the existing prefix. An interrupted card is asked again, while completed rows remain. Keep **both** files private and return them together to the study owner, separately from the other reviewer. Existing answer streams without a binding cannot resume through this command; start a new stream. The packet runner checks structure and resume alignment; only the owner's later `roguard-review-audit` can check its bytes against the attested source. The tool cannot check a person's identity, independence, or interpretation.

After two answer streams have been collected, `roguard-review-audit review_runs/pilot-0035 reviewer-a-answers.jsonl reviewer-b-answers.jsonl` checks the owner map against the attested batch, verifies both packet hashes and every abstract card, and requires each answer stream to follow its assigned packet's exact opaque-ID order and category before computing agreement. For an independent batch it also requires both private packet bindings, so answers cannot silently resume against changed packet bytes. Swapped, reordered, or changed files fail. It returns counts and row numbers without card text, opaque IDs, or reference labels. This verifies file and ID alignment and packet binding, not the reviewers' independence or the correctness of their judgments. Preserve the original answer streams, packet bindings, and any later adjudication separately.

After a **separate, complete adjudication stream** has been returned, `roguard-human-eval-registered review_runs/study review_runs/a-answers.jsonl review_runs/b-answers.jsonl review_runs/adjudicated.jsonl eval/prospective/frozen-predictions.json --output review_runs/human-eval.json` compares model decisions to those declarations. It first runs the packet and answer audit, then checks adjudicated IDs, language, source-batch bytes, and prediction alignment. For an **independent** batch the prediction file must have exactly `schema_version: 2`, `packet_sha256`, `language`, `category`, `model_id`, and `predictions`; each row contains only the opaque `item_id`, `predicted` (`[]` or `["D1"]`/`["S1"]`), and boolean `strict_parse`, in reviewer-a packet order. The evaluator joins opaque IDs to source IDs privately after verifying the packet bytes. The registered-study command also checks that `model_id` matches the verified pre-author freeze in the batch provenance; it refuses a swapped prediction identifier. This checks a declared identifier, **not** whether the named model actually ran. The original `roguard-human-eval` command remains pinned for the pre-author V16 input-integrity record; use `roguard-human-eval-registered` for new independent studies. The older source-ordered schema v1 remains accepted for generator-origin demonstration batches only. A failed parse must have an empty prediction and is counted as an abstention. No `expected` field or text is accepted. The command reports TP/FP/FN/TN on complete adjudications, abstentions, recall counting positive abstentions as misses, raw contrast pairs, adjudicated one-fact pairs, author and factor surfaces, descriptive Wilson intervals, and always/never-review references. For independent batches, it checks the [predeclared abstract-task target](HUMAN_VALIDATION_PROTOCOL.md#4-evaluate-and-state-the-supported-claim); generated batches have no applicable target. Ambiguous adjudications remain outside the confusion counts. Agreement with author-intended labels is reported separately and never substituted for adjudicated labels. The output contains counts and hashes, not cards or IDs. Packet, source, provenance, taxonomy, review, answer, prediction, and both private packet-binding bytes are rechecked before the report returns, so a file changed during evaluation fails. `annotation_packet_binding_verified` and the two binding hashes appear in the public report when both are present; an older generated demonstration without bindings reports false. The output file is created privately and cannot overwrite an existing report. Keep reviewer streams under `review_runs/`; freeze weights, prompt, and cutoff before authors write the new test cards, then commit and push the prediction file under `eval/prospective/` **before** the labeled batch files and before opening adjudicated labels. The [prediction-seal guide](STUDY_PREDICTION_SEAL.md) gives the order and Git-history check. The command cannot verify that timing, reviewer independence, model execution, or label validity; its corresponding flags remain false. A study owner must supply external evidence separately.

For a newly approved **Romanian** independent batch, first run `roguard-independent-check --batch batch-XXXX` and `roguard-blind-packets --batch batch-XXXX --category D1 --output-dir review_runs/batch-XXXX`. Give the model operator **only** `review_runs/batch-XXXX/reviewer-a.jsonl`, without the source batch, provenance, owner map, or adjudications. Install `.[train]`, fetch the pinned mmBERT base, and run `roguard-predict-abstract --packet review_runs/batch-XXXX/reviewer-a.jsonl --base-model-path "$MMBERT_PATH" --adapter models/ro-mmbert-v16-abstract --output eval/prospective/batch-XXXX-v16.json`. The packet declares D1 or S1; the command requires Romanian, checks packet structure, scores each abstract card at the adapter's fixed manifest cutoff, and includes the full adapter-weight hash in `model_id`. It cannot establish that the packet came from an approved independent batch; the evaluator later checks its hash against the attested source. It refuses Ukrainian packets and an existing output file. The selected V16 adapter has a failed cross-surface record and is a research baseline. Freeze its weights, prompt, cutoff, and command version before authors start the new batch; commit and push predictions before the labeled batch files or adjudicated judgments are revealed. Neither the command nor a Git hash verifies that chronology or the human declarations.

`roguard-agreement-batch first.jsonl second.jsonl` compares two streams of D1/S1 evidence cards. Each JSONL line is `{"item_id":"abstract_01","card":{...}}`, where `card` is an ordinary contract input containing `language` and exactly one `disclosure` or `support` card. Item IDs must be distinct, opaque, 1–64 ASCII letters/digits/underscores/hyphens, and identical as a set in both streams. The tool aligns by ID even when row orders differ, then requires the same language and category per item. It fails before printing a report if alignment is invalid. The output gives row numbers in the first stream for differing declarations or incomplete judgments, a pass/review confusion matrix per category, the decision agreement rate on pairs where both judgments are complete, and Cohen's kappa when its denominator is defined. It never returns IDs, card values, or message text. A perfect agreement score would still not prove label validity, reviewer independence, or language quality; all three verification flags remain false.

The [Romanian demonstration streams](../examples/annotation_demo_ro_a.jsonl) and [Ukrainian demonstration streams](../examples/annotation_demo_uk_a.jsonl) are **invented flag cards**, not actual reviewer data. Try:

```sh
roguard-agreement-batch examples/annotation_demo_ro_a.jsonl examples/annotation_demo_ro_b.jsonl
roguard-agreement-batch examples/annotation_demo_uk_a.jsonl examples/annotation_demo_uk_b.jsonl
```

For an individual card outside a packet, a reviewer can append one content-free D1 row with `roguard-review-card --language ro --item-id abstract_01 --compact >> reviewer-a.jsonl` (or `uk`), using the predetermined opaque ID. Add `--category S1` for an S1 item. The app cannot establish that reviewers worked independently or that IDs refer to the intended source cards; a study owner must verify both and check annotations against the exact taxonomy version. Do not place messages, realistic paraphrases, reviewer names, or private source material in these JSONL files or this repository. Review disagreement is a reason to revise the rubric or adjudicate, never a reason to infer a child's credibility.

For a reviewer-led D1 check without storing any message, start from [Romanian](../examples/reviewer_evidence_ro.json) or [Ukrainian](../examples/reviewer_evidence_uk.json) evidence templates. All facts begin as `null`, so `roguard examples/reviewer_evidence_ro.json` returns `INSUFFICIENT_CONTEXT`. A reviewer may replace each `null` with a verified role or boolean after inspecting material outside this repository. The CLI cannot verify that judgment. The [Romanian before](../examples/contrast_disclosure_before_ro.json) and [after](../examples/contrast_disclosure_after_ro.json) cards change only the declared safety/support anchor; the [Ukrainian before](../examples/contrast_disclosure_before_uk.json) and [after](../examples/contrast_disclosure_after_uk.json) cards use the same typed rule while its taxonomy remains a draft. Run `roguard-contrast` on either pair to see the D1 decision change without input text or values in the report.

## Compare a model on abstract contrast pairs

For a **new independently authored** abstract batch, follow the [intake contract](INDEPENDENT_BATCH_INTAKE.md) first. `roguard-author-kit new`, `assemble`, and `seal` provide the [offline author workflow](AUTHOR_KIT.md): separate balanced tasks bound to a pre-author model freeze, a private pending candidate, and intake only after a distinct content-review declaration. After that approval and independent taxonomy reviews, `roguard-independent-check --batch batch-XXXX` checks exact bytes, author balance, and declared D1/S1 factor coverage without printing cards. It cannot verify people, the semantic factor changes, or judgments. `roguard-blind-packets` then accepts the batch for blinded annotation. `roguard-pairs` deliberately rejects its author-intended labels; use `roguard-human-eval-registered` only after separate adjudication. That evaluator counts a pair toward its predeclared numeric target only when the adjudicated declarations differ on exactly the factor named in provenance.

`roguard-pairs --batch batch-0013 --predictions eval/runs/ro-v5-margin-test-0013.json` reads an attested local batch and a model prediction file. The file must name that batch in `batches` and contain a `predictions` or `outputs` array in batch order. Every row needs `id`, `predicted` (category-code array), and `strict_parse` (boolean). Extra fields such as raw outputs or scores are allowed; any supplied `expected` label must agree with the attested batch. Use `--output new-report.json` to write a hash-bound report once, or omit it for stdout. The report includes exact cards and pairs, correct-direction flips, false reviews on negative cards, and per-category precision and recall. It evaluates abstract symbolic cards only and does not estimate accuracy on real child language.
